# FurkVPN для iOS

Клиент FurkVPN для iPhone, iPad и Mac (iOS 15+, macOS 12+ через Mac Catalyst): SwiftUI-приложение и расширение Packet Tunnel с тем же ядром
Xray-core и той же Go-обёрткой (`core/libxray`), что в Android-приложении ([furkvpn-android](https://github.com/foxodever/furkvpn-android)).

```
FurkVPN/      приложение: экраны (Views/), подписка и API (Http.swift), VPN-профиль (VPNController.swift),
              команды для «Быстрых команд» и Siri (Intents.swift), демо-данные для скриншотов (Demo.swift)
FurkTunnel/   расширение Packet Tunnel: ядро Xray на utun-дескрипторе туннеля
Shared/       общее для обоих: модели, хранилище в App Group, обёртка над ядром (Core.swift), сообщения
project.yml   описание проекта для XcodeGen (FurkVPN.xcodeproj в git не хранится)
build.sh      сборка на macOS: ядро → Frameworks/Libxray.xcframework, проект, IPA
build-mac.sh  приложение для Mac (Mac Catalyst) после build.sh → zip
build-appstore.sh  сборка для App Store, подписанная Furry LLC, и загрузка в TestFlight
screenshots.sh  скриншоты в симуляторе и на Mac (демо-сборка)
```

## Как это работает

- Ключ, подписка, зеркала, `x-hwid` и прочие заголовки, API furkapp.net — как в Android (см. [README Android-приложения](https://github.com/foxodever/furkvpn-android#readme)).
  `x-device-os: iOS`, модель — вида `iPhone15,3` (на Mac — `macOS`, версия macOS и модель вида `Mac15,3`, `Platform.swift`). HWID хранится в связке ключей «только на этом устройстве»:
  переустановка приложения — то же устройство, новый iPhone из резервной копии — новое.
- Разбор ключа и подписки, правила маршрутизации и сборка конфига туннеля написаны на Go
  (`core/libxray/keys.go`, `subscription.go`, `routes.go`, `tunconfig.go`) — это перенос Kotlin-кода
  Android-приложения вместе с его тестами. Swift только показывает экраны и управляет VPN.
- Приложение складывает подписку (`subscription.json`, `subscription_configs.json`) и настройки в общий
  контейнер App Group `group.com.furkvpn.app`. Расширение при запуске берёт оттуда выбранный сервер и правила,
  собирает конфиг (`BuildTunnelConfig`: вход TUN, DNS через модуль Xray по TCP, свои правила перед правилами
  сервера) и запускает ядро на utun-дескрипторе туннеля (`StartTunnel`).
- **Соединения ядра привязаны к сети телефона**: расширение узнаёт физический интерфейс (`en0`/`pdp_ip0`,
  NWPathMonitor) до запуска ядра, и `BuildTunnelConfig` с `interface` ставит `sockopt.interface` всем исходящим и
  `autoOutboundsInterface` TUN-входу (на Apple — `IP_BOUND_IF`). Без этого на iPhone соединения ядра к серверам
  уходили в его же туннель (петля): VPN «подключён», трафика нет, расширение не отвечает (1.1.1–1.1.4). Смена
  интерфейса (Wi-Fi ↔ сотовая) перезапускает ядро уже с новым. Интерфейс — `Core.physicalInterfaces`: сначала те,
  через которые идёт путь, и только с адресом (`UsableInterfaces`): включённый, но никуда не подключённый Wi-Fi
  iOS тоже перечисляет, а сокет, привязанный к нему, получает «network is unreachable» (1.1.8 на сотовой
  привязывался к `en0`). Перед запуском ядра и после смены сети `ProbeNetwork` спрашивает DNS 77.88.8.8 без
  привязки и через каждый интерфейс сразу: ядро привязывается к первому, через который ответ пришёл, без
  привязки — если прошёл только такой запрос. В режиме отладки та же проверка идёт ещё и до настроек туннеля,
  а в отчёт попадают путь по iOS (статус, причина, интерфейсы) и адреса интерфейсов. 1.1.9 на телефоне: до
  туннеля сеть у расширения есть, после `setTunnelNetworkSettings` путь `unsatisfied (notAvailable)` и любой
  сокет расширения, даже привязанный к `pdp_ip0`, — «network is unreachable»: iOS не выпускает провайдера мимо
  его туннеля. Поэтому в режиме отладки с туннелем пробуются и другие пути: `NWConnection` (как есть и с
  `requiredInterface`), `createTCPConnection` из NetworkExtension и сокет к 77.88.8.1, который в этом режиме в
  `excludedRoutes`. «Диагностика VPN» показывает подписи приложения и расширения (ID подписи, команда,
  application-identifier, networkextension, App Group — `SignatureInfo` читает их из Mach-O) и
  embedded.mobileprovision обоих: по ним iOS сопоставляет расширение с приложением.
- **Режим совместимости для переподписанных IPA** (1.1.11). Сервисы подписи с одним App ID на сертификат
  подписывают и приложение, и расширение одним профилем: у расширения application-identifier приложения и нет
  своего embedded.mobileprovision. iOS тогда не считает расширение провайдером туннеля: после
  `setTunnelNetworkSettings` всё, что оно шлёт через основной интерфейс, отбрасывается («network is
  unreachable», в т. ч. `NWConnection` и `createTCPConnection`), проходят только адреса из `excludedRoutes` и
  сокеты, привязанные к второстепенному интерфейсу (мобильные данные при Wi-Fi). Если Bundle ID при подписи
  не совпадает с App ID профиля, ещё и сообщения приложения не доходят до расширения — Bundle ID стоит менять
  на App ID профиля (`com.FPR.89ec675` → расширение `com.FPR.89ec675.tunnel`). Поэтому до настроек туннеля
  расширение резолвит адреса серверов и вписывает их в конфиг (`PinTunnelServers`, как в пинге), и они вместе с
  DNS-серверами для их имён уходят в `excludedRoutes` (всегда). Если после настроек запрос без привязки к
  DNS не из этого списка не проходит, включается режим совместимости: ядро без привязки, правила «напрямую»
  ведут через сервер (`noDirect`, `withoutDirect`) — напрямую из такого расширения ничего не выйдет. При смене
  сервера адреса резолвятся заново и, если изменились, туннель получает новые маршруты. 1.3.0 из TestFlight
  (подпись команды 2N5KR68546) показал то же самое: дело не только в переподписи, режим совместимости
  включается и в нормальной сборке. Причина нашлась в 1.3.3 — маршруты туннеля (следующий пункт): до неё в
  режиме совместимости работали все сборки. Режим остался запасным: он включается, только если проверка
  сети после настроек туннеля не получила ответа. Через 20 с интерфейс телефона спрашивается ещё раз (сеть
  могла быть не готова сразу после смены), и если он отвечает — сеть проверяется заново, один раз на сеть.
- Туннель: 172.19.0.1/30 и fdfe:dcba:9876::1/126, DNS 172.19.0.2 — как в Android. Маршруты — всё адресное
  пространство, а при «Локальная сеть напрямую» (включено по умолчанию) — без домашних сетей, link-local и
  multicast (`TunnelRoutes`, перенос `TunRoutes` из Android 1.7.1: 41 префикс IPv4), плюс 172.19.0.2/32:
  AirPlay, Chromecast и принтеры находятся как без VPN. Переключатель при подключённом VPN меняет маршруты
  туннеля (новые настройки сети и перезапуск ядра). Соединения самого расширения идут мимо туннеля.
- **Ни один маршрут туннеля не начинается с адреса 0.0.0.0 или `::`** (кроме самого маршрута по умолчанию,
  когда «Локальная сеть напрямую» выключена): из маршрутов убраны ещё и 0.0.0.0/8 и ::/8, список начинается с
  1.0.0.0/8 и 100::/8 — как у приложения WireGuard для Apple. Ядро XNU считает маршрутом по умолчанию любой
  маршрут на адрес 0.0.0.0, какая бы ни была маска (`rt_primary_default`, `node_lookup_default` в
  `bsd/net/route.c`): до 1.3.3 первым маршрутом туннеля был 0.0.0.0/5 (и ::/1), ядро принимало туннель за
  основной интерфейс, и соединение, привязанное к настоящему интерфейсу телефона, не находило маршрута —
  «network is unreachable». Отсюда всё сразу: расширение не выходило мимо своего туннеля никуда, кроме
  адресов из `excludedRoutes` (тот самый «режим совместимости» у всех, правила «напрямую» шли через сервер,
  путь у расширения всегда `unsatisfied`), а iOS не могла проверить Wi-Fi, к которой только что подключилась:
  при переходе с мобильной сети на Wi-Fi телефон оставался на мобильной без значка Wi-Fi, пока VPN не
  выключишь (жалоба на 1.3.2).
- **Переподписанные IPA** (сервисы и утилиты подписи часто меняют bundle id и App Group под свой
  сертификат): ID расширения туннеля приложение берёт из своего бандла (`TunnelExtension`), App Group — наша
  или `group.<id приложения>`, если подписчик сделал такую (`Store.groupId`). Конфиг выбранного сервера и
  правила (`TunnelPayload`) приложение передаёт при запуске (`startVPNTunnel(options:)`), в `reload` и в пинге,
  и сохраняет в профиле VPN (`providerConfiguration`) для запусков без приложения — расширению общие файлы не
  нужны. Ошибка запуска или неожиданного отключения приходит в приложение через `fetchLastDisconnectError`
  (iOS 16+). Настройки →
  «Диагностика VPN» показывает ID приложения, расширения и профиля, App Group и последнюю ошибку.
- Смена сервера или правил при подключённом VPN не переподключает VPN: приложение шлёт расширению `reload`,
  и оно перезапускает ядро на том же туннеле. Смена во время подключения отправляется, как только VPN
  подключится (запуск мог прочитать прежний сервер).
- Подписка: добавление ключа и обновления идут по очереди (обновление не перетирает новый ключ, при запуске
  нет двойной загрузки); ключ с доменом, которого больше нет в `allowedSubscriptionHosts`, — ошибка. Конфиги
  серверов сохраняются с `fetchedAt` своего списка: расширение не возьмёт конфиг из другой загрузки.
- **Пинг** всегда в приложении (`PingVia`). При включённом VPN соединения проверки привязаны к сети телефона
  (`sockopt.interface` = `en0`/`pdp_ip0` из `PhysicalNetwork`, на Apple — `IP_BOUND_IF`), и пинг меряет путь
  до сервера, а не через текущий. Но мимо поднятого туннеля iOS пропускает только к адресам из
  `excludedRoutes` (в 1.3.0 с VPN пинговался лишь текущий сервер). Поэтому приложение передаёт в
  `TunnelPayload.servers` имена и адреса серверов всей подписки (`SubscriptionServers`), расширение до
  настроек туннеля резолвит их (`ResolveServers`, не дольше 3 с) и оставляет все вне маршрутов, а перед пингом
  приложение берёт у него карту «имя → адрес» (сообщение `addresses`, `SetServerAddresses`): проверки идут на
  эти адреса без DNS туннеля. Заодно смена сервера обычно не меняет маршруты туннеля. В расширении пинговать нельзя:
  каждая проверка — отдельное ядро Xray, проверка «Автовыбора» сразу стучится во все его 15–20 серверов, а их
  соединения живут до таймаутов — «пинг всех» в 1.1.1 выходил за ~50 МБ, iOS убивала расширение и VPN
  отключался. Как в Android 1.6.2: кнопка пинга не блокируется, повторное нажатие начинает заново; удержание
  сервера, который ждёт в очереди «пинговать все», проверяет его сразу; не больше 6 проверок. Расширение
  держит только рабочее ядро (`SetMemoryLimit(32, 50)` — Go собирает мусор раньше лимита).
  Первый показ списка пингует все серверы, как в Android; в Настройках это можно выключить — «Проверять пинг при
  открытии» (`Store.pingOnOpen`, по умолчанию включено): на старых iPhone «пинг всех» долгий и тратит батарею.
  С «Уведомлениями через VPN» (`includeAllNetworks`) iOS `excludedRoutes` не соблюдает и привязку к `en0` не
  пропускает мимо туннеля — пинг шёл бы через текущий сервер или никуда. Тогда ядро расширения держит **мост для
  пинга** (`core/libxray/pingbridge.go`): SOCKS-вход на `127.0.0.1` со случайным портом (`FreeLocalPort`) и
  паролем на каждый запуск туннеля, первым правилом — сразу наружу (`freedom`, привязан к сети телефона, как всё
  ядро; соединения самого расширения iOS выпускает и при `includeAllNetworks`). Приложение берёт порт и пароль
  сообщением `bridge` и пингует через него (`PingBridged`: у каждого исходящего к серверу —
  `sockopt.dialerProxy` на SOCKS моста). Тест `TestPingBridgedReachesTheServerThroughTheBridge` проверяет весь путь.
- **Смена сети** (Wi-Fi ↔ мобильная, другая Wi-Fi). Сеть — это интерфейс, через который iOS отправляет трафик
  (первый из своих в пути NWPathMonitor), с его IPv4-адресами (`InterfaceSignature`; IPv6 — только пометкой и
  только без IPv4: временные адреса меняются сами). Не «любой интерфейс с адресом»: у только что подключённой
  Wi-Fi адрес появляется за секунды до того, как iOS на неё перейдёт, а сотовая держит свой и под Wi-Fi — 1.3.2
  смотрел на адреса и переход с мобильной на Wi-Fi пропускал. Если путь у расширения `unsatisfied` (режим
  совместимости), берётся `NetworkSignature`: интерфейсы `en…` с адресами, а без них — `pdp_ip0`. Проверка — на
  каждое сообщение пути и раз в 5 секунд. Новая сеть, простоявшая 1 с (пропавшая — 3 с: Wi-Fi может вернуться),
  — ядро останавливается, `ProbeNetwork` решает заново про привязку и режим совместимости (с остановленным
  ядром: иначе запрос без привязки мог бы получить ответ через сам туннель), ядро запускается на новом
  интерфейсе, через 2 с — проверка белых списков. Настройки туннеля заново применяются только в режиме
  совместимости (там всё, до чего достаёт ядро, — адреса вне маршрутов, а они остаются на старой сети; так
  1.3.2 починил переход с Wi-Fi на мобильную). Без сети ничего не делается; следующая сеть, даже та же самая,
  получает всё заново. Адреса серверов при этом не резолвятся заново.
- **Автовыбор** — то же, что в Android-сервисе: новое ядро при смене сети (Wi-Fi ↔ мобильная), раз в 10 секунд
  `AutoSelectCheck` смотрит проверки балансировщика и перезапускает ядро (не чаще раза в 2 минуты), если умерли
  серверы, через которые шёл трафик; после сна дольше 5 минут серверы перепроверяются сразу, а после сна
  дольше 30 минут ядро перезапускается (`woke`): соединения с серверами, в том числе в пулах XHTTP и gRPC,
  заведомо мертвы, и новые запросы висели бы на них минутами — на Mac после нескольких часов с закрытой
  крышкой «VPN не работал». О сне говорит iOS (`wake`) или скачок часов между тиками таймера сети: Mac
  сообщает не всегда. После перезапуска запасным ставится сервер, который был лучшим. Внеочередная перепроверка — не чаще раза в минуту: проверка
  сервера, который не отвечает, оставляет в Xray висеть попытку подключения до перезапуска ядра, и при
  мёртвых серверах раз в 10 секунд это съедало десятки мегабайт памяти расширения.
- В объявлении подписки ссылки нажимаются, как в Android: адреса с http(s), `@имя` → t.me, голые домены
  (`.info`, `.ru`, `.com`, `.net`, `.app`, `.me`) → https (`Linkify`).
- **Режим отладки VPN** (Настройки → Диагностика) действует на одно подключение: через 15 с расширение
  отключает VPN с отчётом в «Последней ошибке», переключатель сам выключается. Отчёт никуда не отправляется.
  Только при подключении из приложения: запуск из «Команд» или переключателем VPN в Настройках iOS идёт без него.
- **Диагностики нет в версии из App Store** (`Platform.fromAppStore`: квитанция App Store называется `receipt`,
  у TestFlight и проверки Apple — `sandboxReceipt`, у Xcode и переподписанных IPA её нет): раздел «Диагностика»
  в Настройках и режим отладки остаются только в TestFlight и переподписанных IPA.
- Ссылки `furkvpn://import?url=…` (их открывает furkapp.net/import на iPhone) добавляют ключ.
- **QR-сканер** (экран приветствия) — ключ с QR-кода камерой или с фото из галереи.
- **Телевизор** (Настройки → «Подключить телевизор», если есть камера): QR-код с экрана FurkVPN на Android TV
  (`https://furkapp.net/tv/<код>`, `TvCodeFromLink`) после подтверждения отправляет ключ этого телефона в
  `POST /api/v1/tv/send`. Ссылки `furkvpn://tv/<код>` — то же.
- **Быстрые команды и Siri** (iOS 16+, `Intents.swift`): «Подключить VPN», «Отключить VPN», «Включить или
  выключить VPN», «Подключить к серверу» (сервер из подписки; при включённом VPN — переключение) и «Статус VPN»
  (да/нет для условий в автоматизациях) — без открытия приложения; фразы Siri («Включи FurkVPN», «Выключи
  FurkVPN», «Подключи FurkVPN к серверу», «Статус FurkVPN») работают сразу на iOS 17+, команды видны в
  «Командах» и на кнопке действия. Профиль VPN создаётся первым подключением в приложении (там iOS спрашивает
  разрешение).
- **Кнопка FurkVPN для Пункта управления, экрана блокировки и кнопки действия** (iOS 18+, расширение
  `FurkWidget`, `com.furkvpn.app.widget`): включает VPN, если он выключен, иначе выключает. Кнопка, а не
  переключатель: у расширения виджетов нет App Group, чтобы знать состояние VPN (его и так видно в строке
  состояния). Контролы выполняются в расширении виджетов, у которого нет доступа к VPN, поэтому
  `ToggleVPNControlIntent` (`ControlIntent.swift`, собирается в обе цели) — `LiveActivityIntent`: такие iOS
  выполняет в процессе приложения, и работу делает только копия приложения (флаг `FURK_APP`). На Mac
  расширения нет (`platformFilter: iOS`).
- **Виджет FurkVPN** для главного экрана (малый и средний) и экрана блокировки (круглый, прямоугольный,
  строкой), iOS 18+, то же расширение `FurkWidget` (`StatusWidget.swift`): подключён ли VPN и сколько времени,
  сервер, тариф и сколько дней осталось (закончилась — красным), круглая кнопка включает и выключает VPN тем же
  `ToggleVPNControlIntent`. Без ключа — «Добавьте ключ в приложении». Данные виджету оставляют приложение
  (`AppModel.watchWidgets`: ключ, тариф, сервер, состояние VPN — после того как профиль VPN прочитан) и
  расширение туннеля (включился, выключился, сдался, сменился сервер — когда приложение не запущено), и они же
  просят iOS перерисовать виджет (`WidgetState.change` в `Shared/WidgetSnapshot.swift`, только если что-то
  изменилось). Передаются через общую группу связки ключей `2N5KR68546.com.furkvpn.shared`, а не App Group:
  у App ID виджета App Group нет, привязать её можно только на портале разработчика, а `keychain-access-groups`
  с префиксом команды профили App Store разрешают и так (`2N5KR68546.*`). У приложения первой в списке идёт
  своя группа `2N5KR68546.com.furkvpn.app`, чтобы id устройства (x-hwid) оставался там же. Ad-hoc сборка
  (`build.sh`) подписывается без этих групп, на Mac их тоже нет: там виджет только просит открыть приложение.
  На тонированном и прозрачном главном экране (iOS 18+/26) и на экране блокировки iOS рисует виджет одним
  цветом (`widgetRenderingMode` не `.fullColor`): залитый круг кнопки и значок сливались в одно пятно, а флаг
  сервера выходил прямоугольником. Там круг бледный (плотнее, когда VPN включён), цвет оттенка берёт только
  значок (`widgetAccentable`), а из названия сервера убираются эмодзи (`WidgetText.withoutEmoji`).
- **Белые списки** (`Shared/Whitelist.swift`, `core/libxray/whitelist.go` — перенос `WhitelistMonitor` и
  `WhitelistRules` из Android): напрямую, мимо VPN, HEAD-запросы к `whitelist.blockedProbes` (Google) и
  `whitelist.allowedProbes` (VK, Яндекс) из конфига API; отвечают только вторые — оператор включил белые списки,
  сервер переключается на «LTE 🎲» (если не выбран обход «Все операторы»), а когда списки снимут — обратно на
  прежний сервер (`Store.whitelistPrevious`; если его больше нет в подписке — на «Wi-Fi 🎲»), если сервер
  выбирала проверка или стоял обход; ручной выбор не трогается, а выбор сервера вручную забывает и то, что
  приложение переключало само (`Store.selectByHand`). Чтобы сервер не прыгал от случайностей: «белые списки»,
  найденные впервые, перепроверяются через 4 с (`Whitelist.confirmed`), и сервер двигает только вторая
  проверка; сайт без адреса (`pinnedOnly`) не считается закрытым — если не спросили ни один сайт из группы,
  статус `UNKNOWN`, и проверка ничего не меняет (раньше несостоявшийся резолв Google до туннеля давал «белые
  списки» на каждой проверке); «ничего не работает» перепроверяется через 10–15 с, до трёх раз. Карточка «Белые списки» на
  главном экране, «Подробнее» — время, сеть и ответ каждого сайта; переключатель в Настройках (по умолчанию
  включено). Без VPN проверяет приложение (при открытии, смене сети, «Проверить снова»). С VPN — расширение:
  iOS выпускает мимо туннеля только адреса из `excludedRoutes`, поэтому `TunnelPayload.probes` (хосты
  проверочных сайтов) резолвятся до поднятия туннеля вместе с серверами подписки и исключаются из маршрутов, и
  проверка идёт на эти адреса с SNI по имени (`WhitelistCheck` с `pinnedOnly`: хост без адреса не ищется через
  VPN). Расширение проверяет через 2 с после старта, на новой сети, после долгого сна, раз в 5 минут и по
  сообщению `whitelist` от приложения; переключив сервер, перезапускает ядро на нём и шлёт Darwin-уведомление
  (`SharedChange`), по которому открытое приложение обновляет выбранный сервер и показывает сообщение. Мимо VPN
  при этом для всех приложений идут только эти несколько адресов. Запросы — с User-Agent Go, без FurkVPN, без
  переиспользования соединений и редиректов. Пока белые списки включены, пинг проверяет только серверы из
  `whitelist.pingServers`.
  Чужой VPN (`OtherVPN.swift`): чужие профили VPN приложению не видны, но пока какой-то VPN включён, его
  туннельный интерфейс (`utun…`, `ipsec…`, `ppp…`) есть в `__SCOPED__` системных настроек сети
  (`CFNetworkCopySystemProxySettings`). Если он есть при выключенном нашем VPN (одновременно работает только один),
  проверка через приложение пошла бы через чужой VPN и увидела бы всё открытым: её нет, сервер не переключается,
  карточка и «Подробнее» предупреждают.
- **Уведомление «VPN остановлен»** (Настройки, по желанию, `FurkTunnel/StopNotices.swift`): расширение
  сообщает причину, если iOS остановила VPN не по команде пользователя (`stopTunnel` с причиной), если оно само
  сдалось (ошибка перезапуска ядра), и когда белые списки сменили сервер. Если iOS убила расширение (память),
  `stopTunnel` не вызывается — поэтому расширение держит уведомление, запланированное на +60 с, и каждые 20 с
  сдвигает его; при чистой остановке и во сне (`sleep()`) снимает, в `wake()` ставит снова.
- **Уведомления через VPN** (Настройки, по умолчанию включено; iOS 16.4+, только сборка с нашей App Group, не
  Mac — `AllNetworks` в `VPNController.swift`), как в Happ и Incy. Push-уведомления Apple (APNs) iOS держит вне
  любого VPN, и там, где оператор режет серверы Apple или включает белые списки, уведомления Telegram и других
  приложений не приходят. Профиль VPN с `includeAllNetworks = true` и `excludeAPNs = false` пускает в туннель
  весь трафик телефона, APNs тоже; звонки и СМС оператора, AirDrop, CarPlay и часы остаются напрямую (значения
  iOS по умолчанию), локальная сеть — при «Локальная сеть напрямую» (`excludeLocalNetworks`). Это настройка
  профиля, а не туннеля: применяется при следующем запуске, поэтому смена переключателя (и «Локальной сети
  напрямую») при включённом VPN переподключает его (`reload` → `reconnect`), а при выключенном сразу
  сохраняет профиль — для запусков из «Команд», Пункта управления и on-demand; профиль старой сборки
  обновляется при запуске приложения, если VPN выключен. Цена: `excludedRoutes` iOS больше не соблюдает (пинг
  идёт через мост, см. «Пинг»; режим совместимости переподписанных IPA на них держится — отсюда проверка App
  Group), а пока туннель поднимается или перезапускается, сети у телефона нет совсем. Известная проблема iOS
  (Mullvad, 2025–2026): обновление приложения при включённом VPN с этим флагом может оставить телефон без
  сети до перезагрузки — проверить на TestFlight перед тем, как оставлять включённым по умолчанию для всех.
  В «Диагностике VPN» — строка «Уведомления через VPN».
- **Согласие на обработку данных** (`Views/ConsentView.swift`, правило App Store 5.4 для VPN): при первом
  запуске поверх экрана карточка «Мы обрабатываем ваши данные» — коротко что и зачем, «Подробнее» раскрывает
  остальное (прокручивается внутри карточки), «Согласиться» / «Отказаться». Пока согласия нет, приложение ничего
  не отправляет: `onResume` (конфиг, подписка, тариф) не идёт, ключ из ссылки `furkvpn://` ждёт согласия, команды
  и Пункт управления отвечают «Откройте FurkVPN и согласитесь…». Отказ — вместо приложения экран «Без согласия
  VPN не работает» с кнопкой «Посмотреть ещё раз», VPN выключается. Хранится версия принятого текста
  (`Store.consentVersion`; поднять `consentCurrent`, если текст расширится). Текст должен совпадать с
  furkvpn.info/privacy. В демо-режиме согласие считается данным.
- **«Купить тариф» и «Продлить»** на карточке тарифа — только для России (`PurchaseRegion` в `AppModel.swift`):
  регион телефона RU или страна аккаунта App Store RUS (`Storefront.current`, StoreKit 2). В остальных
  странах App Store ссылка на оплату вне App Store нарушает правило 3.1.1. В демо-режиме (скриншоты для App
  Store) кнопок нет.
- **Переподключаться автоматически** (Настройки, по желанию): правило on-demand `NEOnDemandRuleConnect`
  на любой сети — iOS сама поднимает VPN, если он упал или расширение выгружено. «Отключить» в приложении,
  командах и Пункте управления сначала выключает правило, иначе iOS включила бы VPN обратно. Режим отладки
  подключается без правила (его самопроверка отключает VPN нарочно).
- **Liquid Glass** на iOS 26 (сборка Xcode 26 и новее): кнопка
  подключения, выбор сервера, кнопки сайта/бота/поддержки, вкладки серверов, сообщения и кнопки экрана
  приветствия, карточки тарифа и объявления — стекло поверх фона с мягким свечением фирменного цвета.
  Карточки главного экрана (сервер, белые списки, тариф, объявление) — стекло с плотным оттенком цвета карточки
  (`cardSurface`): иначе свечение фона окрашивало нижнюю карточку светлее верхних; закончившийся тариф — красный. На iOS 15–18 — прежний плоский вид (`Views/Glass.swift`: всё стеклянное за
  `#if compiler(>=6.2)` и `#available(iOS 26.0, *)`). Настройки → Интерфейс → «Стекло» (только iOS 26+): «Жидкое
  стекло» (по умолчанию; само следует системной настройке — «Прозрачное/Тонированное» в iOS 26.1, ползунок в
  iOS 27, «Понижение прозрачности»: Apple применяет её ко всем приложениям с Liquid Glass, а прочитать её
  приложению нельзя), «Матовое стекло» (размытый материал без преломления) и «Без стекла» (плоский вид iOS 15–18);
  `GlassStyle` в `Glass.swift`, хранится в общих настройках, экраны перерисовываются сразу. Кнопки в шапке и шторки iOS 26 рисует своим стеклом сама: при «Матовом» и «Без стекла» приложение убирает и его (`barItem`/`barGroup` — кнопки шапки без стеклянной капсулы, `sheetGlass` — фон шторки), при «Жидком» оставляет системным. Снимки `pro-dark-matte-*` и `pro-dark-flat-*` в `screenshots.sh` (`-demoGlass`). Список серверов на узком экране — шторка на полэкрана (iOS 16+).
- **Широкое окно** (от 700 pt: iPad, окно Mac, раскрытый iPhone Duo) — как на Android: на одной половине главный
  экран (кнопка подключения, под ней карточки), на другой — список серверов (`ServersPane` в `Views/ServersView.swift`)

  экрана, Split View, Slide Over и узкое окно Mac дают обычную колонку со шторкой серверов.
- **iPhone Duo** (складной): сборка с iOS 27.1+ SDK (Xcode 27), поэтому приложение занимает оба экрана целиком,
  а не окно с чёрными полями. Внутренний экран шире, чем высота, и не держит приложение в портрете. Кнопки в

- **iPad**: все ориентации, Split View и Slide Over; подсветка кнопок под курсором; меню команд с клавиатуры

- **Mac** — два пути, оба только через Mac App Store (Apple разрешает VPN-расширение приложения на Mac только там,
  [TN3134](https://developer.apple.com/documentation/technotes/tn3134-network-extension-provider-deployment)):

  **Mac Catalyst** (`build-mac.sh`, Apple silicon и Intel): те же цели с теми же bundle id (одна покупка на все

- В настройках — политика конфиденциальности и пользовательское соглашение (`site.domain`/privacy, /terms);
  «Войти через сайт» сразу открывает личный кабинет.

Чего нет по сравнению с Android: приложений без VPN (iOS не даёт VPN-приложению выбирать приложения),
раздачи интернета, журнала подключений, определения белых списков, импорта и экспорта настроек.

## Ядро

`core/` — копия Go-обёртки над Xray-core из [furkvpn-android](https://github.com/foxodever/furkvpn-android) (там она собирается в `libxray.aar`)
плюс то, что нужно только iOS: разбор ключа и подписки, правила, сборка конфига туннеля (`keys.go`,
`subscription.go`, `routes.go`, `tunconfig.go`), маршруты туннеля (`tunroutes.go`), код телевизора (`tv.go`)
и вызовы для Swift (`apple.go`). Это перенос Kotlin-кода Android-приложения: его изменения (KeyParser,
SubscriptionParser, RouteRules, XrayConfigBuilder, TunRoutes, TvPairing) нужно переносить сюда вместе с тестами;
перенесено всё по Android 1.9.1. Общие файлы (пинг, `pin.go`,
`dnsfix.go`, `hysteria.go`, версия Xray в `go.mod`) правятся в обоих репозиториях: исправление в одном нужно
перенести в другой. Отделено от Android-репозитория 2026-11-02 (ветка `ios`, коммит 92632d7) вместе с историей
iOS и ядра.

## Сборка

Нужны macOS с Xcode, Go (версия из `core/go.mod`), gomobile и XcodeGen:

```bash
cd core && go install golang.org/x/mobile/cmd/gomobile golang.org/x/mobile/cmd/gobind && gomobile init
brew install xcodegen
./build.sh                    # → build/FurkVPN-<версия>-unsigned.ipa
```

Без Mac собирает **Codemagic** (`codemagic.yaml`, Mac mini M2, Xcode 27.2) — с 2026-11-18: у GitHub Actions
бесплатные macOS-минуты приватного репозитория кончаются за 5–6 сборок (минута macOS идёт за десять), а оплату
из России GitHub не принимает. У Codemagic 500 бесплатных минут macOS в месяц, поэтому сборка не стартует на пуш:
её запускают через API (`POST https://api.codemagic.io/builds`, `appId` 6afce9fa265c8601bb721fc5, `workflowId`
`ios`, ветка `main`; токен — `/root/furkvpn-secrets/codemagic.token`) или кнопкой в Codemagic. Метки из сообщения
коммита или `FURK_FLAGS` при запуске: `[testflight]`, `[mac]`, `[shots]`, `[shots-wide]` — как ниже. Секреты
подписи — в группе переменных `signing` (secure). Ядро пересобирается только при изменении `core/` (кэш
`Frameworks/` с хэшем исходников). Результаты — артефакты сборки (IPA, Mac zip, `FurkVPN-shots.zip`, журналы)
через Builds API. Снимки Mac — окно 1440×900 (16:10, размер App Store для Mac).

GitHub Actions (`.github/workflows/ios.yml`, образ `xcode-27`, самый новый Xcode 27 на нём) остался запасным и
запускается только вручную (`workflow_dispatch`): IPA, `FurkVPN-<версия>-mac-unsigned.zip` и концы журналов сборки (`errors-mac.txt`,
`build-mac-tail.log` — для Mac) кладутся в ветку `ios-build` (её можно забрать ключом деплоя) и в артефакты
запуска; `xcode.txt` там же — какие Xcode были на машине и каким собрано. Сборка для Mac — отдельный шаг: если она
сломается, IPA всё равно будет. Приложение для Mac подписано ad-hoc **без** прав (Mac не запускает приложение,
которое заявляет VPN и App Group без профиля), поэтому показывает только интерфейс; VPN заработает в сборке,
подписанной аккаунтом разработчика для Mac App Store.

**Скриншоты без iPhone**: если в сообщении коммита есть `[shots]`, workflow после IPA запускает
`screenshots.sh` — демо-сборку (флаг `DEMO`, `Demo.swift`: примерные серверы, тариф и «подключено»; в IPA её
нет) в симуляторе на iPhone SE, iPhone Pro, Pro Max, iPhone Duo (раскрытый `duo-open-*` — внутренний экран,
сложенный `duo-folded-*` — внешний), iPad Pro 13 и iPad mini, в тёмной и светлой теме: приветствие, главный
экран, подключено, серверы, настройки, на широких — ещё список слева (`6-left`) → `shots/` в `ios-build`. Затем
демо-сборка для Mac (`mac-*`): окно 1200×820 и узкое 440×820, тема и размер — аргументами запуска
(`-demoTheme`, `-demoWindow`); каждый снимок дважды — `screencapture` окна и `*-app.png`, нарисованный самим
приложением (на случай, если раннеру нельзя записывать экран). Шарнир Duo в `simctl` не двигается, поэтому скрипт
собирает маленькую программу, которая просит об этом тестовую службу SpringBoard внутри симулятора (как
devicehubctl); если она не сработала — снимки обоих экранов как есть (`duo-inner-*`, `duo-outer-*`, погасший
выходит чёрным).
VPN в симуляторе не работает (там нет Network Extension) — только интерфейс. Фреймворк ядра собирается и для
симулятора (`iossimulator/arm64`) и для Mac Catalyst (`maccatalyst/arm64`, `maccatalyst/amd64`).

**IPA без подписи.** Она подписана ad-hoc с нужными правами (Network Extension, App Group). Поставить её как есть
можно через TrollStore; иначе её нужно переподписать сертификатом разработчика с профилями для
`com.furkvpn.app` и `com.furkvpn.app.tunnel`, в которых есть Network Extensions (Packet Tunnel) и App Group
`group.com.furkvpn.app`. VPN-расширение работает только с платным аккаунтом Apple Developer.

быть новым. `PrivacyInfo.xcprivacy` в приложении и в расширении — причины для API из обязательного списка Apple
(UserDefaults, даты файлов, время с загрузки), без них App Store Connect сборку не принимает.
